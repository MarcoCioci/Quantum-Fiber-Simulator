========================================================
1. GENERAL REPOSITORY ORGANIZATION
========================================================

The repository is structured as a modular scientific environment,
not as a single monolithic LaTeX document.

Current structure:

text/
├── archive/
├── derivations/
├── notes/
├── sources/
└── thesis/

Purpose of each directory:

archive/
    Deprecated material, old drafts, legacy versions,
    experimental structures no longer actively maintained.

derivations/
    Standalone analytical derivations and mathematical expansions.
    Used for validation and theoretical support.
    NOT necessarily intended for direct inclusion in thesis chapters.

notes/
    Temporary reasoning, advisor discussions, TODOs,
    exploratory ideas, future directions, PMD notes,
    implementation planning.

sources/
    Scientific references:
    books, papers, lecture notes, tomography references,
    Nielsen & Chuang, Bell papers, etc.

thesis/
    Final manuscript-oriented material.
    This is the actual report-class thesis repository.

========================================================

========================================================

The thesis now follows a report-class hierarchy.

Mandatory hierarchy:

\chapter

\subsection

Avoid using:

except inside numerical experiments where a fixed structure exists.

========================================================
8. LATEX WRITING POLICY
========================================================

--------------------------------------------------------
8.1 Structural Hierarchy
--------------------------------------------------------

Use:

\chapter
\section
\subsection

Subsubsections:
ONLY inside Chapter 5 experiments.

--------------------------------------------------------
8.2 Paragraph Policy
--------------------------------------------------------

Allowed paragraph types:

\paragraph{Interpretation.}
\paragraph{Role in the modeling hierarchy.}
\paragraph{Operational implications.}
\paragraph{Implementation.}

Forbidden:

\paragraph{Simulation notes.}

Rule:
Every paragraph must add conceptual value.

--------------------------------------------------------
8.3 Spacing Policy
--------------------------------------------------------

Use:

\medskip

ONLY for semantic transitions.

Correct usage:

Concept introduction

\medskip

Formal equation

\medskip

Interpretation

Avoid:
- repeated consecutive \medskip
- spacing after every equation

========================================================
10. MATHEMATICAL CONSISTENCY
========================================================

--------------------------------------------------------
10.1 General Rules
--------------------------------------------------------

- Define symbols before using them
- Keep notation globally consistent
- Avoid repeated equations nearby

Preferred notation:

F  -> fidelity
γ  -> purity
C  -> concurrence

--------------------------------------------------------
10.2 Equation Policy
--------------------------------------------------------

Number equations ONLY if:

- referenced later
- structurally important
- reused
- experimentally relevant

Always use:

\label{eq:name}

Reference with:

\eqref{eq:name}

Never reference equations manually.

========================================================
11. MATHEMATICAL TYPESETTING STANDARD
========================================================

--------------------------------------------------------
11.1 Inline Mathematics
--------------------------------------------------------

Preferred syntax:

\( ... \)

Example:

The phase parameter \( \theta \) controls the evolution.

--------------------------------------------------------
11.2 Display Mathematics
--------------------------------------------------------

Use:

\[
...
\]

for central equations.

Example:

\[
|\psi(\theta)\rangle
=
\frac{1}{\sqrt{2}}
\left(
|01\rangle + e^{i\theta}|10\rangle
\right)
\]

--------------------------------------------------------
11.3 Multi-Line Equations
--------------------------------------------------------

Use:

\begin{align}
...
\end{align}

Align at "=".

--------------------------------------------------------
11.4 Operators
--------------------------------------------------------

Use standard operators:

\sin
\cos
\exp
\log
\Tr

Never write:

sin(x)

Use:

\( \sin(x) \)

========================================================
12. QUANTUM MECHANICS NOTATION
========================================================

Mandatory conventions:

Kets:
\( |\psi\rangle \)

Bras:
\( \langle\psi| \)

Inner products:
\( \langle\phi|\psi\rangle \)

Tensor product:
\( \otimes \)

Expectation values:
\( \langle O \rangle \)

Correlators:
\( \langle \sigma_i \otimes \sigma_j \rangle \)

--------------------------------------------------------
12.1 Hilbert Spaces
--------------------------------------------------------

Use:

\( \mathbb{C}^2 \)

Composite systems:

\( \mathbb{C}^2 \otimes \mathbb{C}^2 \)

========================================================
13. SYMBOL CONVENTION POLICY
========================================================

Header comments and theoretical text:
use symbolic notation.

Examples:

θ
ρ
σ
⊗
⟨ ⟩

Inline MATLAB comments:
prefer ASCII-safe notation.

Examples:

theta
rho
sigma_x

Avoid hybrid notation.

Correct:

psi_out = ...

or

\( |\psi_{\mathrm{out}}\rangle \)

Never mixed forms.

========================================================
14. IMPLEMENTATION DISCUSSION POLICY
========================================================

Implementation text should describe:

- computational methodology
- simulator architecture
- theory-to-code mapping

NOT:
- software documentation

Localized implementation remarks should appear
ONLY when the mapping is genuinely non-trivial.

========================================================
15. MATLAB CODE STYLE POLICY
========================================================

Functions follow standardized structure:

1. Header
2. Objective
3. Inputs
4. Outputs
5. Robustness checks
6. Main computation

Typical structure:

function out = my_function(in)

% =========================
% Robustness checks
% =========================

% =========================
% Main computation
% =========================

end

Purpose:
maintain analytical traceability
between theory and implementation.
